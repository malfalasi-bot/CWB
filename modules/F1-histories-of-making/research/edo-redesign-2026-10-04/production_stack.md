# Production stack for award-level interactive course units at scale, zero software cost

Scope: architecture, content model, rendering, narration, assets, data backbone, hosting, QA, effort. Research date 2026-10-04. Sources are official docs, repos, model cards and first-hand maker accounts wherever found; secondary summaries are flagged.

## Q1. What architecture lets authors write beats as data (text + scene directives) and get a consistent unit without hand-coding each one?

### Takeaway
The proven newsroom pattern is "copy as structured data" (ArchieML from Google Docs, or YAML/JSON files) feeding a component framework with a sticky-graphic + stepped-text "scrolly" component; The Pudding ships exactly this as an open SvelteKit starter. For a 39-unit course with ~60 reference pages, Astro's Content Layer (Zod-validated collections of YAML/JSON/MDX, with Svelte/other islands for heavy scenes) adds schema enforcement, cross-collection references and static output that the Pudding starter lacks; scrollama (MIT) or CSS scroll-driven animations drive the beat triggers.

### Cited Findings
- The Pudding's `svelte-starter` is a SvelteKit template "designed around data-driven, visual stories", featuring "ArchieML for micro-CMS powered by Google Docs and Sheets", Style Dictionary for CSS/JS parity, CSV/JSON/SVG imports, and "SSR static-hosted builds by default". Copy is pulled with `npm run gdoc` from a shared Doc/Sheet ID in `google.config.js`. It ships a `Scrolly.svelte` component plus `Slider`, `Tap`, `MotionToggle`, `reducedMotion` and `scrollY` stores, and a `useFetcher` helper — [the-pudding/svelte-starter](https://github.com/the-pudding/svelte-starter)
- Multiple published Pudding stories (e.g. outliers, banknotes, word-game, location-game) are forks of this same starter, each linking an "ArchieML Doc" and a draft Google Doc — evidence the template is their production pipeline — [the-pudding/outliers](https://github.com/the-pudding/outliers)
- Scrollama: "modern & lightweight JavaScript library for scrollytelling" using IntersectionObserver rather than scroll events; MIT licence; v3.2.0 as of Aug 2026 — [russellsamora/scrollama](https://github.com/russellsamora/scrollama); [cdnjs scrollama](https://cdnjs.com/libraries/scrollama)
- Closeread (Quarto extension for scrollytelling) is built on scrollama v3 and "distributed under an MIT License" — an existing example of authoring scrolly units as text/markup rather than code — [Closeread guide](https://closeread.netlify.app/guide/index.html)
- Astro content collections: every collection has a required `loader` and optional Zod `schema`; built-in `glob()` loader reads Markdown, MDX, Markdoc, JSON, YAML, TOML; `file()` loads arrays from a single JSON/YAML/TOML file (custom `parser` for CSV); "If any file violates its collection schema, Astro will provide a helpful error"; Astro auto-generates JSON Schema files into `.astro/collections/` so YAML/JSON data files get editor IntelliSense/validation (Red Hat YAML extension) — [Astro content collections](https://docs.astro.build/en/guides/content-collections/)
- Astro's Content Layer API loads data "from any source" at build time, caches between builds, and custom loaders can skip unchanged sources via a metadata store (e.g. If-Modified-Since) — [Astro Content Layer deep dive](https://astro.build/blog/content-layer-deep-dive/); loader `schema`/`createSchema()`, `parseData()` and `renderMarkdown()` are documented in [Content Loader API](https://docs.astro.build/en/reference/content-loader-reference/)
- CSS scroll-driven animations (`animation-timeline: scroll()/view()`) are compositor-driven, no JS; sources conflict on Firefox: one 2026 post says Firefox stable still gates them behind a flag (~82.6% global support, Interop 2026 priority) — [ZKO World](https://zko.world/blog/css-scroll-driven-animations-progressive-enhancement-quick-take); a Mozilla Connect thread dated Jan–Mar 2026 has developers still requesting Firefox support — [Mozilla Connect](https://connect.mozilla.org/t5/ideas/implement-css-scroll-driven-animations-animation-timeline/idi-p/116931); contradicted by [Empire UI](https://empire-ui.com/blog/css-scroll-driven-advanced) and [codingdunia](https://codingdunia.com/blog/scroll-driven-animations-css-guide) which claim Firefox support (these are secondary blogs; treat with caution). A production case used the official scroll-timeline polyfill for non-Chromium browsers — [Medium/Coolen](https://medium.com/@petercoolen/css-scroll-driven-animations-aa9aa198f430)
- GSAP (incl. ScrollTrigger, SplitText, Flip, formerly paid "Club" plugins) is "now free for everyone, thanks to Webflow's support" — [gsap.com](https://gsap.com/scroll). Note: GSAP is free-of-charge but under its own Standard License, not an OSI open-source licence (licence text not fetched here — see Gaps).

### Inferences
- Beat schema (recommended, derived from Pudding/Closeread patterns): `unit.yaml` → `beats[]` each with `id`, `text` (Markdown), `scene` (component name), `props` (e.g. `map: {center, zoom, layers[], highlight[]}` / `image: {iiif, region}` / `model: {glb, camera}`), `audio` (narration file id + transcript ref), `sources[]` (claim ids). Astro's Zod schema validates each beat at build; `z.enum` on `scene` prevents unknown directives; `reference()` links beats to people/places/objects collections.
- Astro + a Svelte (or vanilla) island for the sticky scene is the lowest-code path: Astro renders text, nav, transcripts, references as static HTML (fast, accessible, indexable); one `Scrolly` island per unit receives the beats array and dispatches `props` to a scene registry. Authors never touch components after the registry exists.
- The Pudding starter is the best reference implementation for component ergonomics (reduced-motion store, Scrolly, Slider/Tap for touch) and can be mined under its licence; but its Google-Docs dependency requires internet at author time, which this project's authoring environment lacks — write YAML/Markdown in-repo instead and run any Doc→ArchieML sync in GitHub Actions if ever needed.
- Use scrollama or IntersectionObserver for beat *triggering* (deterministic, testable, works everywhere) and CSS scroll-driven animations only as progressive enhancement for decorative motion; avoid GSAP unless its licence terms are reviewed and accepted.

### Gaps
- GSAP Standard License text and whether it is acceptable under a strict "open licences only" rule was not fetched (only the "free for everyone" banner was seen).
- NYT and Reuters do not publish a current open story template comparable to the Pudding starter in the results retrieved; no NYT/Reuters open-source scrolly repo was confirmed in this pass.
- Exact Firefox shipping status of scroll-driven animations as of Oct 2026 is unresolved (conflicting secondary sources).

## Q2. MapLibre globe vs d3 (vs deck.gl): which gives a Pacific-centred, dateline-safe world map with raster historical overlays most cheaply, and what are the gotchas? (Plus IIIF, 3D and animated-lecture renderers.)

### Takeaway
For a static or lightly animated Pacific-centred world/regional map with vector data, d3-geo is cheapest and intrinsically dateline-safe (it cuts at the antimeridian during projection and supports arbitrary rotation). For zoomable raster historical maps (tiles, terrain, warped IIIF scans) use MapLibre GL JS (BSD-3; globe projection since v5.0, Jan 2025), accepting known globe-raster gotchas (polar blurriness, seams, antimeridian query bugs fixed only in 2025). Allmaps lets you warp any IIIF-hosted historical map client-side in MapLibre without pre-tiling. OpenSeadragon (BSD-3) handles deep-zoom images; model-viewer (Apache-2.0) covers 3D; Motion Canvas (MIT) is the open choice for narrated animated lectures, Remotion is free only for teams ≤3 people.

### Cited Findings
- d3-geo: "the input geometry is first converted to radians, rotated on three axes, clipped to the small circle or cut along the antimeridian"; `projection.rotate([lambda, phi, gamma])` applies yaw/pitch/roll; `geoClipAntimeridian` cuts crossing geometries "in two, one on each side" — [D3 projections](https://d3js.org/d3-geo/projection)
- D3 "represents geometry in spherical coordinates and then cut[s] along the antimeridian during projection", enabling "arbitrary spherical rotations during projection without visual artifacts", unlike software relying on pre-cut shapefiles — [Observable: Antimeridian cutting](https://observablehq.com/notebook-kit/ex/d3/antimeridian-cutting)
- d3-geo winding-order gotcha: exterior rings for polygons smaller than a hemisphere must be clockwise — the opposite of GeoJSON RFC 7946; standard GeoJSON "may require stitching to remove antimeridian cuts" — [d3-geo README v3.1.0](https://github.com/d3/d3-geo/blob/v3.1.0/README.md)
- MapLibre: "Globe View or Globe Projection was released as part of MapLibre GL JS 5.0.0 in January 2025"; not available in MapLibre Native — [MapLibre roadmap: Globe View](https://maplibre.org/roadmap/maplibre-gl-js/globe-view/)
- Globe implementation: raster layer was the first adapted; globe "will automatically transition to mercator at high zoom levels" (animated, nearly unnoticeable) — [PR #3783](https://github.com/maplibre/maplibre-gl-js/pull/3783)
- Globe raster gotchas (maintainer comments): "raster source is currently visually unappealing at the globe projection (at low zoom, at poles...)"; looking at the pole changes the zoom level/tile set; seams between tiles of different zooms are handled with a stencil trick — [issue #5436](https://github.com/maplibre/maplibre-gl-js/issues/5436); [custom tiles on globe example](https://maplibre.org/maplibre-gl-js/docs/examples/add-a-custom-layer-with-tiles-to-a-globe/)
- Antimeridian bugs on globe: `queryRenderedFeatures` with a bbox crossing the antimeridian returned wrong results (issue Jan 2025) and was fixed by splitting the bbox in PR #5856 (May 2025); z0 tile antimeridian overdraw is clipped in the fragment shader (`clipAntimeridian`) — [issue #5381](https://github.com/maplibre/maplibre-gl-js/issues/5381); [PR #5856](https://github.com/maplibre/maplibre-gl-js/pull/5856); [ProjectionData docs](https://maplibre.org/maplibre-gl-js/docs/API/type-aliases/ProjectionData/)
- Allmaps: "georeference any map from any institution that supports IIIF"; "doesn't need to generate XYZ map tiles"; warps "on-the-fly, in the browser"; Georeference Annotations are "an approved extension to the IIIF Presentation API"; plugins exist for MapLibre, OpenLayers, Leaflet; Allmaps Tile Server converts annotations to XYZ tiles; the Editor/Viewer are static sites; "core components ... are open source" — [allmaps.org](https://allmaps.org/); monorepo packages include `@allmaps/maplibre`, `@allmaps/render` (WebGL2/Canvas/IntArray renderers) — [allmaps/allmaps](https://github.com/allmaps/allmaps/); CLI can fetch full IIIF images, write a GeoTIFF script, then `gdal2tiles.py --xyz` for static tiles — [@allmaps/cli](https://npmx.dev/package/@allmaps/cli)
- OpenSeadragon: "open-source, web-based viewer for zoomable images, implemented in pure JavaScript"; "released under the New BSD license" — [openseadragon README](https://github.com/openseadragon/openseadragon); supports DZI and IIIF tile sources, and recommends VIPS `dzsave` for tiling — [Creating Zooming Images](https://openseadragon.github.io/examples/creating-zooming-images/)
- `<model-viewer>`: Google web component to "display interactive 3D models on the web and in AR", glTF/GLB, package licence Apache-2.0 — [model-viewer package.json via issue #824](https://github.com/google/model-viewer/issues/824); Draco mesh compression is Apache-2.0 — [Draco README](https://github.com/polygonjs/polygonjs/blob/b95eb0f68d39473ba7d74bdb5a4cface8943a123/public/three/js/libs/draco/README.md)
- Smithsonian Voyager: "Open source 3D explorer and authoring tool suite" (Explorer web component; Story for annotations/articles/tours); uses its own SVX format modelled on glTF — [Voyager docs](https://smithsonian.github.io/dpo-voyager); [COPTR entry](https://coptr.digipres.org/Smithsonian_Voyager)
- Motion Canvas: "TypeScript library that uses generators to program animations" plus a real-time editor, "designed to create informative vector animations and synchronize them with voice-overs"; repo shows MIT license, 19k stars — [motion-canvas/motion-canvas](https://github.com/motion-canvas/motion-canvas). A maintainer discussion proposed switching to GPL (works made with it unaffected; "official decision has not yet been made" at that time) — [Discussion #1015](https://github.com/orgs/motion-canvas/discussions/1015)
- Remotion: free for individuals, "organizations with 3 or fewer people", and non-profits, with no functional difference; a Company License is triggered by >3 employees OR operating an automation that programmatically calls `renderMedia()`/CLI; Automators tier is $0.01/render with $100/month minimum — [Remotion License FAQ](https://www.remotion.dev/docs/license/faq)

### Inferences
- Decision rule: (a) World/region context beats, routes, trade flows, animated transitions between projections → d3-geo + TopoJSON (ISC/BSD, tiny, SVG/Canvas, trivially Pacific-centred via `rotate([-150,0])`, cut-safe). (b) Zoom into a historical scan or terrain, or let the learner pan → MapLibre with raster/terrain sources and Allmaps-warped IIIF overlays. (c) deck.gl only if you need tens of thousands of points/arcs in WebGL; otherwise it is extra weight (no deck.gl-specific evidence collected — see Gaps).
- For MapLibre, start in Mercator (not globe) for raster historical overlays: globe raster is explicitly described as unappealing at low zoom/poles, and globe-specific antimeridian fixes landed only in 2025. If a globe is wanted for the "Pacific hemisphere" opening beat, use d3's `geoOrthographic` (no tiles needed) or a MapLibre globe with vector-only basemap, then crossfade to Mercator for the detailed overlay.
- Georeference the Edo-period and Dutch/Portuguese maps in Allmaps Editor (zero infrastructure, outputs an open Georeference Annotation JSON) and either render live via `@allmaps/maplibre` (requires the holding institution's IIIF server to stay up) or bake XYZ tiles with Allmaps CLI + GDAL in GitHub Actions for robustness. Baking is preferred for a course that must work for years.
- For narrated "animated lecture" segments, Motion Canvas (MIT today) is the only option that is both open and designed around voice-over sync; Remotion's automation clause would be triggered by a CI render pipeline for 38 units, so treat Remotion as non-free for this workflow even with a ≤3-person team.

### Gaps
- Smithsonian Voyager's licence was not confirmed from an official page in this pass (expected Apache-2.0; verify in repo LICENSE).
- deck.gl and MapLibre terrain (raster-dem) specifics were not researched; Mirador licence not confirmed (commonly Apache-2.0; verify).
- No head-to-head benchmark of d3 vs MapLibre for historical narrative maps was found; the comparison above is inferred from capabilities and known issues.

## Q3. State of open TTS for narration in 2026 (quality, licences, English + Japanese names), and is narration worth the cost?

### Takeaway
Two Apache-2.0 options cover this project: Kokoro-82M (tiny, CPU-friendly, phoneme-controllable via misaki, 24 kHz, English strong, Japanese voices present but graded C/C−) and Qwen3-TTS (0.6B/1.7B, Apache-2.0, 10 languages incl. English and Japanese, natural-language style control, voice design, 3-second cloning, GPU-oriented). Piper is MIT but older-sounding; XTTS-v2 ("other"/non-commercial CPML), Fish-Speech/OpenAudio S1 (CC-BY-NC-SA) and F5-TTS (CC-BY-NC) are excluded by licence. Narration is cheap to produce once text is final; the real cost is pronunciation QA for Japanese names and keeping audio in sync with text edits — manage it with per-beat audio files keyed to a text hash.

### Cited Findings
- Kokoro-82M: licence Apache-2.0, 127M downloads; v1.0 trained on "a few hundred hrs" for "$1000 for 1000 hrs" of A100; trained "exclusively on permissive/non-copyrighted audio data and IPA phoneme labels" — [Kokoro-82M model card](https://huggingface.co/hexgrad/Kokoro-82M/raw/70bb171837b48bc81a57a8f5d63ea1e655c54ab6/README.md); HF metadata shows `license:apache-2.0` — [HF repo](https://hf.co/hexgrad/Kokoro-82M)
- Kokoro languages/voices: American English 11F 9M, British 4F 4M, Japanese 4F 1M (voices graded C+ to C−, trained on minutes to a few hours), Mandarin, Spanish, French, Hindi, Italian, Brazilian Portuguese; warning that non-English support "may be absent or thin due to weak G2P and/or lack of training data" — [VOICES.md](https://huggingface.co/hexgrad/Kokoro-82M/blob/main/VOICES.md)
- Kokoro runtime: `pip install kokoro`; G2P via `misaki` (`misaki[ja]` for Japanese, espeak-ng fallback for English out-of-dictionary words); outputs 24 kHz; best on 100–200 tokens per chunk, weak under 10–20 tokens, rushes over 400 — [hexgrad/kokoro](https://github.com/hexgrad/kokoro?tab=readme-ov-file); [model card](https://huggingface.co/hexgrad/Kokoro-82M/raw/4d240409f7eed58ba22a40e921be104b0ef9f958/README.md). An NVIDIA ONNX port lists English "full support" and Japanese/Mandarin/etc. "partial support" — [nvidia/kokoro-82M-onnx-opt](https://huggingface.co/nvidia/kokoro-82M-onnx-opt)
- Qwen3-TTS (released 2026-01-22): Apache-2.0 models and tokenizers; 10 languages (Chinese, English, Japanese, Korean, German, French, Russian, Portuguese, Spanish, Italian); 0.6B and 1.7B variants; CustomVoice models with 9 preset speakers (incl. English "Ryan", "Aiden", Japanese "Ono_Anna") controllable via natural-language `instruct`; VoiceDesign from text descriptions; Base models do 3-second voice cloning; trained on >5M hours; streaming latency 97 ms — [QwenLM/Qwen3-TTS](https://github.com/QwenLM/Qwen3-TTS?dejam_ab=i9-rtC); [arXiv 2601.15621](https://arxiv.org/abs/2601.15621); [Qwen3-TTS-12Hz-1.7B-Base on HF: license apache-2.0](https://hf.co/Qwen/Qwen3-TTS-12Hz-1.7B-Base). Reported WER 1.24 on Seed-TTS test-en — [Qwen3-TTS changelog](https://qwenlm-qwen3-tts.mintlify.app/resources/changelog). Example code uses `device_map="cuda:0"`, bf16, flash-attention — GPU assumed.
- Piper voices: MIT licence, ONNX, ~35 languages listed (no Japanese tag in the list) — [rhasspy/piper-voices](https://hf.co/rhasspy/piper-voices)
- XTTS-v2: HF licence field "other" (Coqui Public Model License, non-commercial) — [coqui/XTTS-v2](https://hf.co/coqui/XTTS-v2)
- Fish-Speech 1.5 and OpenAudio S1-mini: CC-BY-NC-SA-4.0 (S1-mini gated); F5-TTS: CC-BY-NC-4.0 — [fish-speech-1.5](https://hf.co/fishaudio/fish-speech-1.5); [s1-mini](https://hf.co/fishaudio/s1-mini); [SWivid/F5-TTS](https://hf.co/SWivid/F5-TTS)
- Motion Canvas is explicitly built to "synchronize [animations] with voice-overs" — [motion-canvas](https://github.com/motion-canvas/motion-canvas)

### Inferences
- Kokoro is the pragmatic default for English narration: CPU inference fits a GitHub Actions runner (no GPU needed), and misaki accepts phoneme overrides so Japanese names (e.g. Tokugawa Ieyasu, Dejima, Sakoku) can be pinned via a shared pronunciation lexicon rather than hoping the G2P guesses right. Qwen3-TTS 0.6B is the upgrade path if a GPU runner (or a one-off local render) is available and more natural prosody or a Japanese-native speaker voice for Japanese-language quotations is wanted.
- Versioning: store `narration/<unit>/<beat-id>.<sha8-of-text>.mp3|opus` plus a JSON transcript with word timings; CI regenerates only beats whose text hash changed. This keeps audio and captions provably in sync and makes diffs reviewable. Captions/transcripts come free from the source text (TTS input), satisfying WCAG without ASR.
- Worth it? Audio generation cost ≈ minutes of CPU per unit; QA cost is the pronunciation pass (hours). Given Motion Canvas-style lecture segments and accessibility, narration is worth including for the lecture/summary beats, but keep scrolly beats text-first (Pudding analytics note that most readers skip extras — see Q8) and make audio optional.

### Gaps
- No independent 2026 MOS/listening benchmark comparing Kokoro vs Qwen3-TTS vs Piper for long-form educational narration was found; quality statements rely on the vendors' own cards and the Kokoro voice grades.
- Misaki's exact custom-phoneme syntax for English text was not fetched (the misaki README was not read); verify before relying on it.
- Qwen3-TTS CPU feasibility and GitHub Actions runtime were not tested or documented in retrieved sources.
- Whether Kokoro's English voices pronounce romanised Japanese acceptably without overrides is unknown — test with the unit's name list.

## Q4. What do zero-cost hosts allow (bandwidth, file sizes, build minutes) for a site with ~15 MB of images per unit (≈600 MB for 39 units + references)?

### Takeaway
GitHub Pages (1 GB site, 100 GB/month soft bandwidth, 10-minute deploy timeout, unlimited Actions minutes on public repos) and Cloudflare Pages (20,000 files, 25 MiB per file on Free) both fit a ~0.6–1 GB static course; Cloudflare R2 adds 10 GB free storage with free egress for images if the site outgrows Pages. Netlify's 2025 credit-based Free plan (300 credits/month, 15 credits per production deploy) is now the weakest fit for a frequently rebuilt site.

### Cited Findings
- GitHub Pages: source repo recommended ≤1 GB; "Published GitHub Pages sites may be no larger than 1 GB"; deployments "timeout if they take longer than 10 minutes"; "soft bandwidth limit of 100 GB per month"; soft limit of 10 builds/hour which "does not apply if you build and publish your site with a custom GitHub Actions workflow"; not for commercial/e-commerce hosting — [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)
- GitHub Actions: "free for standard GitHub-hosted runners in public repositories"; private repos get a plan-dependent quota of free minutes and storage — [Actions billing and usage](https://docs.github.com/en/actions/administering-github-actions/usage-limits-billing-and-administration)
- Cloudflare Pages (Free): up to 20,000 files per site (100,000 on paid plans); "maximum file size for a single Cloudflare Pages site asset is 25 MiB"; 100 custom domains — [Cloudflare Pages limits](https://developers.cloudflare.com/pages/platform/limits)
- Cloudflare R2 free tier: 10 GB-month storage, 1M Class A and 10M Class B operations per month, "Egress (data transfer to Internet): Free"; paid storage $0.015/GB-month — [R2 pricing](https://developers.cloudflare.com/r2/pricing#frequently-asked-questions)
- Netlify legacy Free plan: 100 GB/month bandwidth (hard limit), 300 build minutes/month (hard limit); new credit-based plans from 5 Sep 2025: Free = 300 credits/month, Production deploys cost 15 credits each, preview/branch deploys free, compute 5 credits per GB-hour — [Netlify legacy plans](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-legacy-plans/legacy-pricing-plans); [Netlify credit-based plans changelog](https://www.netlify.com/changelog/netlify-pricing-update-introducing-credit-based-plans); [Netlify pricing](https://www.netlify.com/pricing)

### Inferences
- Capacity arithmetic: 39 units × 15 MB + ~60 reference pages ≈ 0.6–0.7 GB — under GitHub Pages' 1 GB cap but with little headroom for deep-zoom tile pyramids or audio. Put narration audio and IIIF/DZI tile pyramids on Cloudflare R2 (free egress) or a second Pages project, and keep the main site lean; alternatively host the whole site on Cloudflare Pages where the 20,000-file cap (not size) is the binding constraint — a DZI pyramid of a 10k×10k image alone is ~2,000 tiles, so tile pyramids should also go to R2.
- Bandwidth: 100 GB/month on GitHub Pages ≈ 6,600 full-unit loads at 15 MB; fine for a course cohort, marginal for a viral unit. Cloudflare Pages/R2 removes that ceiling.
- Build: a custom Actions workflow (recommended anyway for TTS, tiling, Playwright) removes the 10-builds/hour limit; keep each deploy under 10 minutes by caching generated assets (audio, tiles, depth maps) as build artifacts or committing them to an assets repo.
- Netlify's Free plan allows at most 20 production deploys/month under the new credits — unsuitable as the primary host for an actively edited course.

### Gaps
- Cloudflare Pages Free build count per month (the docs page's "Builds" section was truncated; commonly 500/month) and any bandwidth caps on Pages static assets were not captured from the official page — verify.
- GitHub Free plan's exact private-repo Actions minutes (commonly 2,000/month) not confirmed from the fetched page.

## Q5. Assets pipeline: fetching open-access images by API (with etiquette), tiling, depth maps, georeferencing, fonts

### Takeaway
Met, Cleveland and AIC need no key; Smithsonian uses an api.data.gov key (1,000 req/h); LoC publishes per-endpoint per-minute caps; Wikimedia requires a descriptive User-Agent, serial requests and `maxlag` for bots. Generate all derivatives in GitHub Actions: `vips dzsave` for DZI/IIIF-level-0 pyramids, Depth Anything V2 Small (Apache-2.0) for 2.5D depth, Allmaps for georeferencing.

### Cited Findings
- Met Collection API: no key; "Please limit request rate to 80 requests per second"; `/v1/search` is deprecated and "will be retired on October 1, 2026" in favour of paginated `/v1.1/search` (default 100, max 500 per page, offset+limit ≤ 10,000); bulk work should use the Open Access CSV — [metmuseum.github.io](https://metmuseum.github.io/). Object JSON exposes `isPublicDomain`, `primaryImage` (full-res), `primaryImageSmall` (web-large), `additionalImages`; images are static JPEGs, not IIIF — [Met API reference notes](https://github.com/huytieu/cog-second-brain/blob/main/skills/museum-art/references/met.md) (secondary)
- Art Institute of Chicago: anonymous users "throttled to 60 requests per minute" per IP; `limit` ≤ 100 and ≤ 10,000 records per query; IIIF Image API 2.0 at `https://www.artic.edu/iiif/2/{id}/full/843,/0/default.jpg` recommended because it is cached; other cache-friendly widths 200/400/600/843, and 1686 for public-domain works — [AIC API docs](http://aggregator-data.artic.edu/docs/). Secondary reports say the IIIF host needs a `Referer: www.artic.edu` header and `image_id` must be requested via `fields` — [Navigating.art 2026](https://www.navigating.art/articles-from-navigatingart/open-access-2026)
- Cleveland Museum of Art: CC0 datasets for >64,000 records and images for >37,000 works; no key; API returns up to 1,000 records per call; full dataset mirrored on GitHub — [CMA Open Access API](https://openaccess-api.clevelandart.org/). Image tiers `images.web` (900 px), `images.print` (3400 px), `images.full` (TIFF) — [CMA reference notes](https://github.com/huytieu/cog-second-brain/blob/main/skills/museum-art/references/cleveland.md) (secondary)
- Smithsonian Open Access API: routed via api.data.gov, API key required; api.data.gov default 1,000 requests/hour per key; `DEMO_KEY` 30/hour per IP; CC0 per media item — [source-permissions research notes](https://github.com/TomGranot/faceless-channel-factory/blob/main/docs/research/source-permissions-collection-and-package.md) (secondary, cites api.data.gov manual); IDS deliveryService URL accepts `&max=` to cap longest edge — [Smithsonian reference notes](https://github.com/huytieu/cog-second-brain/blob/main/skills/museum-art/references/smithsonian.md) (secondary)
- Library of Congress JSON API: no key; documented 20 JSON requests/minute, 150 image-service requests/minute, 150 storage-service requests/minute; exceeding can trigger a one-hour block; robots.txt disallows crawling HTML search — same secondary source as above
- Wikimedia API etiquette: "no hard speed limit on read requests, but be considerate"; making requests "in series rather than in parallel" yields a safe rate; batch multiple items per request; use `maxlag` for non-interactive tasks; set a descriptive `User-Agent: clientname/version (contact information...)` or `Api-User-Agent` from browsers; requests without a meaningful User-Agent may be blocked — [API:Etiquette](https://mediawiki.org/wiki/Special:MyLanguage/API:Etiquette); [API:Etiquette (Wikimedia guidelines section)](https://www.mediawiki.org/wiki/API:Etiquette/id); [Wikimedia Analytics access policy](https://doc.wikimedia.org/generated-data-platform/aqs/analytics-api/documentation/access-policy.html)
- libvips `dzsave`: builds pyramids with `--layout dz|zoomify|google|iiif|iiif3`; default DeepZoom 254 px tiles + 1 px overlap ("256x256 jpeg files for centre tiles, the most efficient size"); can write to `.zip`/`.szi` containers; `--id` sets the IIIF `info.json` base; `--skip-blanks`, `Q` quality — [Vips.Image.dzsave](https://www.libvips.org/API/current/method.Image.dzsave.html); [Building image pyramids](https://www.libvips.org/API/current/making-image-pyramids.html); IIIF layout "still missing the `full/` stuff ... simple to fix in a post-process step" — [libvips issue #1465](https://github.com/libvips/libvips/issues/1465). Worked example: `vips dzsave image.png out --tile-size 512` + OpenSeadragon from CDN — [Simon Willison TIL](https://til.simonwillison.net/javascript/openseadragon)
- Depth Anything V2 Small: licence Apache-2.0, relative depth estimation — [depth-anything/Depth-Anything-V2-Small](https://hf.co/depth-anything/Depth-Anything-V2-Small)
- Georeferencing: see Allmaps findings in Q2 (IIIF-based, open annotations, MapLibre plugin, CLI→GDAL tiles).

### Inferences
- Fetcher design (runs in GitHub Actions, never at author time): one `assets.yaml` per unit listing `source` (met|cma|aic|si|loc|commons), `id`, `crop`, `credit`; a script resolves metadata + licence flag, downloads the largest permitted derivative, writes a sidecar JSON (title, maker, date, credit line, licence, source URL, retrieved-at), and generates WebP/AVIF sizes. Rate-limit per host: serial requests with a descriptive UA for Commons; ≤1 req/s for AIC (its docs ask for ≤1/s and no parallel scrapers); 20/min for LoC JSON.
- Prefer sources that give fixed derivatives (Met `primaryImage`, CMA `print`) for simplicity, and IIIF (AIC, many Japanese institutions, Rijksmuseum, Getty) when deep-zoom is wanted — OpenSeadragon can point straight at a remote IIIF `info.json`, but for longevity bake your own `dzsave --layout iiif3` pyramid to R2.
- 2.5D parallax: run Depth Anything V2 Small on the chosen hero images in CI, store a 512-px depth PNG per image, and displace in a small WebGL/Canvas shader during scroll; the Apache-2.0 licence of the Small model matters because larger V2 variants may carry different terms (not verified here).
- Fonts: not researched this pass (see Gaps); the Pudding starter's Style Dictionary approach for tokens is a good model for theme parity across 39 units.

### Gaps
- Several API details (Met image field names, AIC Referer requirement, Smithsonian `max=` param, LoC per-minute limits) come from secondary notes rather than the institutions' own pages; verify against official docs before coding.
- Fonts (open Japanese-capable families such as Noto Serif/Sans JP; self-hosting vs Google Fonts) and Japanese institutional IIIF endpoints (NDL, ARC, Waseda) were not researched.
- Wikimedia thumbnail-size conventions (standard widths on upload.wikimedia.org) were not captured; only the UA/serial-request/maxlag guidance was confirmed.

## Q6. Data backbone: which shared gazetteer/timeline sources, and what schema for people/places/events/objects/claims?

### Takeaway
Use Wikidata QIDs as the universal join key, World Historical Gazetteer / Linked Places Format for place reconciliation, PeriodO ARK URIs for named periods, and CODH's Edo Maps (7,918 unique Edo place names from 29 NDL kiriezu sheets) plus CODH's Edo-period coastline/road/post-station datasets as the Japan-specific layer; Pleiades is ancient-Mediterranean only and OpenHistoricalMap is ODbL (share-alike). Model content as beats → claims → sources with stable ids and a confidence field.

### Cited Findings
- PeriodO: "documents definitions of historical periods" with stable ARK identifiers; periods modelled as SKOS concepts with OWL-Time bounds and `dcterms:spatial` links to Wikidata/DBpedia/Pleiades; whole dataset downloadable as one JSON-LD file — [PeriodO technical overview](https://perio.do/technical-overview/); partners include China Historical GIS, British Museum, Pleiades — [Digital Classicist wiki](https://wiki.digitalclassicist.org/PeriodO); PeriodO maintains a "historical places" gazetteer keyed to Wikidata classes (historical country, ancient civilization, archaeological site) — [periodo-places](https://github.com/periodo/periodo-places)
- Pleiades: "community-built gazetteer and graph of ancient places", open licence, CSV/JSON/RDF dumps (weekly RDF), Zenodo-archived releases (4.1, May 2025) — [pleiades.datasets](https://github.com/isawnyu/pleiades.datasets); [Zenodo 15540082](https://zenodo.org/records/15540082). Scope is ancient (Mediterranean/Near East), so it is marginal for Edo Japan.
- CODH Edo Maps (江戸マップ): 8,788 place names extracted from 29 NDL "Edo kiriezu" sheets (Owariya edition, 1849–1862), deduplicated to 7,918 unique names (July 2025 dataset); all positions hand-corrected against the "Rekichizu" Edo-style basemap (June 2025, β dropped); 1,220 names linked to the Nihon Rekishi Chimei Taikei place-name dataset (Oct 2025); classification table (facilities, residences, temples/shrines, shops, roads/bridges, towns, water, sights); data collected via IIIF Curation Platform; links to Bukan daimyo residences — [CODH Edo Maps](https://codh.rois.ac.jp/edo-maps/); [About](https://codh.rois.ac.jp/edo-maps/about/)
- CODH historical GIS datasets: late-Edo coastline/water bodies, lakes, major highways, post stations; Edo kiriezu town-block (machiya) polygons; a historical place-name map with 298,914 names served as vector tiles — [CODH 歴史GIS](https://codh.rois.ac.jp/historical-gis/); Nihon Rekishi Chimei Taikei place-name dataset (Heibonsha, 50 vols) — [CODH datasets](https://codh.rois.ac.jp/dataset/)
- World Historical Gazetteer API: returns Linked Places Format v1.1; OpenRefine Reconciliation Service API v0.2 for places and PeriodO periods; searches WHG, GeoNames, Getty TGN, Wikidata (`wd:Q84`), OSM, OpenHistoricalMap (`ohm:`), Pleiades namespaces; licences differ per source — "GeoNames is CC-BY, Wikidata is CC0, OpenStreetMap is ODbL, Getty TGN is ODC-By"; ODbL/CC-BY-SA sources (incl. OpenHistoricalMap) carry share-alike; "Roughly 43% of WHG's indexed records are share-alike" — [WHG API docs](https://docs.whgazetteer.org/content/technical/apis.html)

### Inferences
- Schema (recommended; derived from PeriodO/LPF/Wikidata practice):
  - `people/*.yaml`: `id` (slug), `wikidata` (QID), `names: {en, ja, ja_kana, romaji, order: family-first|given-first, macrons: true}`, `born/died` (EDTF strings), `roles[]`, `sources[]`.
  - `places/*.yaml`: `id`, `wikidata`, `whg`/`codh_edo_id`, `names` (period-specific: e.g. Edo → Tokyo with `valid_from/to`), `geometry` (point or ref to GeoJSON), `period_refs[]` (PeriodO ARKs).
  - `events/*.yaml`: `id`, `when` (EDTF, allow uncertainty `1639?`), `where[]`, `who[]`, `claims[]`.
  - `objects/*.yaml`: `id`, `source_api`, `source_id`, `iiif` or `image`, `licence`, `credit`, `depth_map`.
  - `claims/*.yaml`: `id` (e.g. `c-edo-0042`), `text`, `confidence: high|medium|low|contested`, `sources[]` (citation keys), `checked_by`, `checked_on`, `supersedes`. Beats reference claim ids; the fact-check log (Q7) is just the claims collection's history in git.
- Zod schemas in Astro enforce these at build; `reference('places')` guarantees no dangling ids across 39 units; a CI script cross-checks every QID against a cached Wikidata snapshot (fetched in Actions, since authoring is offline).
- Keep ODbL data (OpenHistoricalMap) only as rendered basemap tiles, not merged into the project's CC-BY/CC0 dataset, to avoid share-alike contamination.

### Gaps
- Licences of CODH Edo Maps and historical-GIS datasets were not captured (CODH typically uses CC BY/CC BY-SA per dataset; verify each page).
- OpenHistoricalMap's time-aware vector tile service and Japan coverage were not checked directly (only its ODbL status via WHG).
- Wikidata property-level guidance (P625, P1448, P580/P582, P6375) was not fetched this pass.

## Q7. Workflow and QA: visual regression, accessibility, performance budgets, fact-check logs, localisation of names, content versioning

### Takeaway
A GitHub Actions gate of Playwright `toHaveScreenshot` (per-beat snapshots at 3 viewports), `@axe-core/playwright` (fail on WCAG 2.x A/AA violations), and Lighthouse CI assertions (`lhci autorun` with `lighthouserc`) is standard, cheap and documented; keep fact-check state in the claims collection and localisation rules (Japanese family-name-first, macrons) as data + a lint rule, and version everything in git with content-hash-keyed generated assets.

### Cited Findings
- Playwright accessibility testing uses `@axe-core/playwright` (`AxeBuilder`), with `.include()` to scope, `.withTags(['wcag2a','wcag2aa','wcag21a','wcag21aa'])` to match WCAG A/AA, scanning the page "in its current state" (so interact first), and `testInfo.attach()` to embed full results — [Playwright accessibility testing](https://playwright.dev/docs/accessibility-testing)
- axe-core is licensed under the Mozilla Public License 2.0 (vendored LICENSE in Playwright repo); `@axe-core/playwright` npm package licence MPL-2.0 — [axe-core LICENSE](https://github.com/microsoft/playwright/blob/4d289016/tests/assets/axe-core/LICENSE); [npm registry](https://registry.npmjs.org/@axe-core/playwright)
- Lighthouse CI pattern: `lighthouserc` with `collect.url[]`, `numberOfRuns: 3`, `assert.assertions` such as `'categories:accessibility': ['error', {minScore: 0.95}]`, `color-contrast: error`; `npx @lhci/cli autorun` exits non-zero on failed assertions; `upload.target: temporary-public-storage` gives a report link — [stellae.design guide](https://www.stellae.design/en/learn/accessibility-automation-in-ci); a real repo runs Lighthouse CI, axe-via-Playwright and visual regression as separate workflows "so a flaky snapshot can't mask a real accessibility / performance regression" — [astraudit quality.yml](https://github.com/BEKO2210/astraudit/blob/a7ef59b953f1d7702c777990441c963e07e37aab/.github/workflows/quality.yml)
- Playwright visual regression: `expect(page).toHaveScreenshot('name.png', {fullPage: true})`, element-level snapshots, viewport variants, `emulateMedia({colorScheme:'dark'})`, config `expect.toHaveScreenshot: {maxDiffPixels, threshold}` — [configure-ux-testing reference](https://github.com/laurigates/claude-plugins/blob/HEAD/configure-plugin/skills/configure-ux-testing/REFERENCE.md) (secondary)
- The Pudding uses "checklists that help authors consider various aspects of their story, like getting regular feedback and conducting accessibility audits" — [Tom Vaillant interview](https://tomvaillant.com/insights/behind-the-scenes-at-the-pudding-creative-processes)
- The Pudding on AI-assisted production: "Critical thinking still falls to the user"; fixing edge cases "can often take days on end" and is "the most deceptively time-consuming" stage; AI chart prototyping reduced "hour-long tasks (for us) to seconds" — [pudding.cool/2024/07/ai](https://pudding.cool/2024/07/ai/)
- Pudding analytics: "most users don't look at all the extra interactions and tooltips; those are for power users" — [Vaillant interview](https://tomvaillant.com/insights/behind-the-scenes-at-the-pudding-creative-processes)

### Inferences
- Snapshot strategy: generate Playwright screenshots per beat by programmatically scrolling to each `beat.id` anchor (deterministic via scrollama step ids) at 390/820/1440 px widths, with `prefers-reduced-motion: reduce` emulated to freeze animations; store baselines in-repo (Linux-only runner to avoid cross-OS font diffs) and require explicit `--update-snapshots` on PRs that intend visual change.
- Budgets: assert `categories:performance ≥ 0.9` and `categories:accessibility ≥ 0.95`, plus resource budgets (e.g. ≤ 2 MB initial transfer, ≤ 300 kB JS) via Lighthouse `resource-summary` assertions; lazy-load MapLibre/OpenSeadragon islands only when a beat needs them.
- Fact-check log = the `claims` collection + git history; CI fails the build if a beat cites a claim with `confidence: contested` without a visible hedge, or a claim lacks `sources`. A `CHECKS.md` per unit is generated from claims (who/when) rather than hand-written.
- Localisation of names: store canonical forms in `people/*.yaml` and render via one `<Name>` component that applies the unit's convention (Japanese order, macrons on/off, kanji on first mention); lint beats for raw name strings to force use of the component.
- Content versioning: units are directories (`units/12-dejima/unit.yaml`, `beats.md`, `assets.yaml`); generated audio/tiles/depth keyed by content hash and stored in R2/an assets repo; a `version` and `changelog` field in `unit.yaml` surfaces on the page for learners/teachers.

### Gaps
- No museum-digital-team QA workflow documentation was found in this pass; the QA pipeline is assembled from web-engineering practice rather than cultural-sector precedent.
- Lighthouse CI official docs page was not fetched (patterns above are from practitioner guides mirroring the official config).

## Q8. Effort: hours/roles per unit from comparable teams, and how to industrialise so the 39th unit costs a fraction of the first

### Takeaway
Comparable makers report 4–6 weeks per visual essay at The Pudding (one journalist-engineer doing research → data → design → code, with a week of exploration first), one week to three months at SCMP depending on data readiness, and ~a year per piece for a solo explorable author (Ciechanowski). Hours are rarely published; the consistent lesson is that research/story and data-cleaning dominate, not coding, and that templates plus "story-first" discipline are what compress later units.

### Cited Findings
- The Pudding: "exploration phase probably takes a week or so and then the whole project would probably take 4–6 weeks", though "sometimes projects take a week, sometimes they take two months"; everyone "works with data — sources it, analyzes it, designs a front-end visual, then posts that up and writes the story" — [Medium Q&A with Ilia Blinderman](https://medium.com/the-idea/q-a-ilia-blinderman-journalist-engineer-at-the-pudding-1798c944241b)
- "On average ... each project takes about a month"; team of six (2019) — [Brandwatch interview](https://www.brandwatch.com/blog/interview-the-pudding-data-visualization/); engineering alone "can take anywhere from a couple of days to a couple of months" — [Storybench](https://www.storybench.org/pudding-structures-stories-visual-essays/)
- Pudding staff spend ~50% of time on Pudding work (rest on Polygraph client work); no deadlines; ~8 staff in 2024 — [Vaillant interview](https://tomvaillant.com/insights/behind-the-scenes-at-the-pudding-creative-processes); [Off Menu interview with Matt Daniels](https://offmenu.substack.com/p/the-proof-is-in-the-pudding)
- Matt Daniels: "we spend a lot of time getting the story right before we start coding"; "entire freelance contracts dedicated to just the story before we even get into production"; contributor projects get a Pudding designer/dev to "fill any gaps" — [Off Menu](https://offmenu.substack.com/p/the-proof-is-in-the-pudding)
- Pudding's process checkpoints: question → data → analysis → storyboard → production, with explicit continue/pivot/put-down decisions; manual data collection can sink "a lot of time" — [Continue, Pivot, or Put it Down](https://pudding.cool/process/pivot-continue-down/)
- SCMP infographics team (six people): a Shenzhen-40-years interactive took "one week on the entire process" because data was available; a protest story planned for 2–3 days "ended up taking two or three months"; a breaking standalone finished in one day — [Nightingale interview](https://nightingaledvs.com/on-the-success-of-the-south-china-morning-post-infographics-team/)
- Simon Scarr (SCMP then Reuters): graphics take "anywhere from an hour or two for simple charts ... to a few weeks"; full-page features planned weeks ahead; a Graphics Coordinator role handled requests, proofing, chasing data — [Visualising Data interview](https://visualisingdata.com/2013/04/interview-with-simon-scarr/)
- Solo explorable author: Ciechanowski publishes roughly one to three interactive articles per year (3/yr in 2020–22, 1 in 2023, 2 in 2024), each taking months of solo research, simulation, interaction design and writing — [Cool People Stories](https://www.coolpeoplestories.com/bartosz-ciechanowski-interactive) (secondary); "Each post takes months to write" — [Ryan Orban notes](https://ryanorban.com/notes/bartosz-ciechanowski-blog/) (secondary)
- Nicky Case's "Adventures with Anxiety" took three people (writing/art/code by one person, music by another, a final-week performance contractor) — [Storybench](https://www.storybench.org/how-nicky-case-designed-the-game-adventures-with-anxiety/)
- Pudding on AI: Claude cut chart-prototyping "hour-long tasks ... to seconds" but produced "sloppiness" needing human edge-case review — [pudding.cool/2024/07/ai](https://pudding.cool/2024/07/ai/)

### Inferences
- Converting published durations into hours: a Pudding 4–6 week essay at ~50% time ≈ 80–120 person-hours per piece; SCMP's one-week team piece with 2 people ≈ 60–80 hours. A reasonable planning range for one Edo unit *after* the template exists: research & claims 15–25 h, writing beats 8–12 h, assets (fetch, crop, credits, depth, tiles) 6–10 h, scene config/build 4–8 h (no new components), narration + pronunciation QA 2–4 h, QA/review 4–6 h ≈ 40–65 h. The first unit, which also builds the template, scene registry, schemas, CI and design system, is plausibly 3–5× that (per Pudding "months coding" and Ciechanowski's year-long solo builds).
- What makes unit 39 cheap: (1) a fixed beat schema and scene registry so authors only write YAML/Markdown; (2) shared gazetteer/people/claims collections that grow with each unit (later units reuse entities and verified claims); (3) an assets manifest + CI fetcher so images arrive credited and sized automatically; (4) narration regenerated only for changed text; (5) baseline screenshots, axe and Lighthouse gates so review is diff-based; (6) Pudding-style checkpoints (question → sources → storyboard) to kill weak units early.
- Roles for a 1–3 person team + agents: one content lead (research, claims, beats), one producer-engineer (templates, scenes, CI, assets), optionally one editor/QA (fact-check sign-off, accessibility, pronunciation). AI agents fit the Pudding's observed sweet spots — drafting fetch scripts, prototyping scenes, first-pass transcripts — with humans owning edge cases and verification.

### Gaps
- No source published explicit hours-per-role for a scrollytelling piece; all figures above are durations or team sizes converted by inference.
- No museum digital-team production accounts (hours per interactive) surfaced in this pass; Reuters Graphics process posts with timings were not found.

## Q9. Recommended zero-cost stack (synthesis)

### Takeaway
Astro (MIT) + Svelte islands, content as Zod-validated YAML/Markdown collections, scrollama (MIT) for beat triggers, d3-geo/TopoJSON for narrative maps and MapLibre GL JS (BSD-3) + Allmaps for zoomable historical overlays, OpenSeadragon (BSD-3) with `vips dzsave` pyramids for artworks, `<model-viewer>` (Apache-2.0) for 3D, Motion Canvas (MIT) for narrated animated segments, Kokoro-82M (Apache-2.0) narration with Qwen3-TTS (Apache-2.0) as the GPU upgrade, Depth Anything V2 Small (Apache-2.0) for 2.5D, Wikidata/WHG/PeriodO/CODH as the data backbone, GitHub Actions for all generation, GitHub Pages or Cloudflare Pages for the site and Cloudflare R2 for heavy assets, and Playwright + axe-core (MPL-2.0) + Lighthouse CI as the quality gate.

### Cited Findings
- Licence/maturity evidence for each component is cited in Q1–Q7 above (Astro content collections docs; scrollama MIT; MapLibre globe v5.0 roadmap; OpenSeadragon New BSD; model-viewer Apache-2.0; Motion Canvas MIT; Kokoro and Qwen3-TTS Apache-2.0; Depth Anything V2 Small Apache-2.0; axe-core MPL-2.0; GitHub Pages/Cloudflare/R2/Netlify limits).

### Inferences
- Avoid: Remotion (automation clause), GSAP unless its non-OSI licence is accepted, XTTS/Fish/F5 (non-commercial), Netlify Free as primary host (20 production deploys/month), MapLibre globe for raster overlays in year one.
- Keep the authoring loop offline-capable: everything that needs the internet (API fetches, Wikidata checks, TTS model download, tiling) runs in GitHub Actions on push; authors only edit YAML/Markdown and review the deployed preview.

### Gaps
- Fonts, Japanese-institution IIIF endpoints, deck.gl, Mirador, Voyager licence, Cloudflare Pages build quota, and GSAP licence terms remain unverified (listed in the relevant sections above).
